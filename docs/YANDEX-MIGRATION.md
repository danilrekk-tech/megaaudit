# Mega.Audit — аудит архитектуры перед размещением фронтенда в Yandex Object Storage

## 1. Что показал аудит проекта

| Вопрос | Факт |
|---|---|
| Какой бэкенд используется | Только серверная часть самого приложения TanStack Start (SSR-воркер на хостинге Lovable). Отдельного бэкенда нет. |
| Lovable Cloud | Не подключён. |
| Supabase | Не подключён, `src/integrations/supabase/*` отсутствует. |
| Supabase project | Отсутствует. |
| Авторизация | Серверной авторизации нет. Служебный раздел `/staff` закрыт локальным PIN `7788` (`src/lib/store.ts`), проверка выполняется в браузере. |
| Пользователи | Не хранятся нигде: таблицы пользователей нет. |
| История аудитов | `localStorage` браузера, ключ `aia.audits.v1`. |
| База услуг и доработок | Файл `src/data/addons.json` (сид) + правки в `localStorage`, ключ `aia.catalog.v1`. |
| Коммерческие предложения | `localStorage`, ключ `aia.proposals.v1`. |
| Внешние AI/API интеграции | AI-моделей и внешних API-ключей нет. Единственный внешний запрос — серверная загрузка HTML проверяемого сайта и страниц `https://megagroup.shop/addon/<id>` для цен. |
| Edge Functions | Нет. Есть две серверные функции TanStack: `detectSiteFormat`, `getAddonPrices`. |
| Environment variables | До этой задачи не использовались ни одной. |
| Секреты | Нет ни одного секрета. |

**Вывод: общей базы данных, общей авторизации и общего хранилища в проекте сейчас не существует.** Все данные — аудиты, каталог, КП, признак входа сотрудника — лежат в браузере конкретного пользователя. Поэтому «одна общая база» и «пользователь из Lovable виден в Yandex» технически недостижимы без создания бэкенда, а создавать его задача прямо запрещает.

Что реально можно и нужно разделить между двумя фронтендами — это две серверные функции. Они и стали общим бэкендом: внешняя сборка обращается к ним по HTTP на домене Lovable.

## 2. Таблица функций и эндпоинтов

| Function | Backend endpoint | Auth | External frontend compatible | Action |
|---|---|---|---|---|
| Определение формата сайта (`detectSiteFormat`) | `POST /_serverFn/...` на домене Lovable | нет, но включён CSRF-фильтр для serverFn | Нет — CSRF-мидлвар блокирует кросс-доменные вызовы | Добавлен публичный эндпоинт `GET /api/public/detect-site?url=` с CORS-белым списком |
| Цены доработок (`getAddonPrices`) | `POST /_serverFn/...` на домене Lovable | нет, CSRF-фильтр | Нет — та же причина | Добавлен публичный эндпоинт `POST /api/public/addon-prices` с CORS-белым списком |
| Запуск аудита (`runAudit`) | нет, считается в браузере | — | Да | Изменений не требуется |
| История аудитов, каталог, КП | `localStorage` браузера | — | Да, но данные не общие между доменами | Изменений не требуется; общими они станут только после появления настоящей базы |
| Вход сотрудника (PIN) | `localStorage` браузера | локальный PIN | Да, но сессия своя на каждом домене | Изменений не требуется |
| Логотип, шрифты, статика | статические файлы сборки | — | Да | Загружаются в бакет вместе со сборкой |

## 3. Как устроена совместимость с двумя хостингами

- `src/lib/api-client.ts` — единая точка выбора адреса бэкенда. Переменная `VITE_API_BASE_URL` пуста → работает прежний путь через серверные функции того же домена (сборка Lovable не меняется). Переменная задана → фронтенд вызывает публичные эндпоинты на указанном домене.
- `src/routes/api/public/detect-site.ts` и `src/routes/api/public/addon-prices.ts` — публичные эндпоинты. Вся логика переиспользована из существующих функций, бизнес-логика не менялась.
- `src/lib/cors.server.ts` — белый список origin'ов. По умолчанию разрешён `https://megaaudit.lovable.app`, превью-домены `*.lovable.app` и localhost. Домен Yandex добавляется переменной `ALLOWED_ORIGINS` (через запятую). `Access-Control-Allow-Origin: *` не используется.
- `vite.config.ts` — при `YANDEX_BUILD=1` включается SPA-режим: собирается статика с одной HTML-оболочкой, пригодная для Object Storage. Без переменной сборка для Lovable остаётся SSR и не затронута.
- Хардкодов `localhost` и `lovable.app` во фронтенд-коде нет; адрес бэкенда задаётся только переменной окружения.

## 4. Проверка сборки

- SSR-сборка для Lovable: `npm run build` — без изменений.
- Статическая сборка: `YANDEX_BUILD=1 VITE_API_BASE_URL=https://megaaudit.lovable.app npm run build` — проходит успешно, результат в `dist/client/`, точка входа `_shell.html` (переименовывается в `index.html` при загрузке).

## 5. Ограничения, о которых важно знать

1. **Общей базы данных нет.** Аудиты, каталог и КП хранятся в браузере. Данные, созданные в версии на Yandex, физически не могут появиться в версии на Lovable, и наоборот. Тест «единый бэкенд» в части данных пройти невозможно, пока в проекте не появится настоящая база. Новый бэкенд по условиям задачи не создавался.
2. **Общей авторизации нет.** PIN проверяется в браузере, пользователей нет. Вход на каждом домене независим.
3. **Object Storage отдаёт только статику.** Серверные функции остаются на домене Lovable — это и есть общий бэкенд для обеих версий.
4. **SEO/SSR.** Версия на Yandex работает как SPA: HTML-разметка формируется в браузере, а не на сервере.
